# 15年整套精听的组装与正式发布

最终交付为15套考试视频和15个整套精听视频。45个A/B1/B2精听片段是制作中间件，每年严格按A→B1→B2组装为一个视频，中文名为`YYYY年 专八听力 精听.mp4`。不把45个片段作为正式15套下载内容，也不伪造整年子段输入或修改原有子段审批接口。

## 独立启动入口

工作流`.github/workflows/assemble-tem8-intensive-full.yml`只监听分支`codex/tem8-listening-2009-2024`上的`.github/tem8-listening-intensive-full.json`。根任务确认实际子段已核并存档后再创建或更新控制文件；本接口文档不是触发控制。

```json
{
  "mode": "complete_intensive_full",
  "years": [2009,2010,2011,2012,2013,2014,2015,2016,2017,2018,2019,2021,2022,2023,2024],
  "assemble": true,
  "collect_runs": [],
  "reuse_child_releases": []
}
```

目标必须恰好是实际15年，拒绝2020、缺年、重复年份和A/B1/B2目标。最多15个年度任务并行，使用独立并发组和仓库内置`GITHUB_TOKEN`，不改主渲染工作流、45子段输入、字体、NLP或原有审批指纹。

每个任务先核当前三个子段的`gate`，再从`tem8-listening-render-cache-2009-2024`续收匹配当前审批的MP4与完整证据包。可选`reuse_child_releases`只添加续收来源，仍逐项验证当前指纹。缺少任何一个当前子段或原声canonical不一致时停止该年，绝不拿旧审批替代。组装器直接使用已核图像码流；原音按子段真实保留区间重建PCM后统一编码一次。独立核验确认视频码流/帧序、PCM、音轨及声画同步，再立即存入`tem8-listening-intensive-full-cache-2009-2024`，临时artifact不是唯一副本。

已有同一组装指纹与真实视频摘要的年度成品会跳过组装。失败重试可用`assemble_years`指定实际年份子集；完整目标`years`仍保留15年。只需恢复发布时设置`assemble=false`，直接续收已核整套缓存；`collect_runs`可追加此前整套工作流运行号，只接受`tem8full-YYYY`完整年度artifact，不把子段或诊断artifact当成整套。

## 组装器与发布器的接口

组装器：`tools/整套精听.py`；独立组装缓存及正式发布器：`tools/整套精听发布.py`。

```bash
python 专八/听力/批量/tools/整套精听发布.py matrix
python 专八/听力/批量/tools/整套精听发布.py collect 2009 --out parts
python 专八/听力/批量/tools/原音准备.py 2009 --out in/audio
python 专八/听力/批量/tools/整套精听.py build 2009 --parts parts --original in/audio/原音.wav --out work
python 专八/听力/批量/tools/整套精听发布.py stage 2009 --parts parts --work work --out up
python 专八/听力/批量/tools/整套精听发布.py store up
python 专八/听力/批量/tools/整套精听发布.py publish --art art --out release-out
```

`parts`下必须有`2009-A`、`2009-B1`、`2009-B2`三个原始stage，各自包含实际MP4、`meta.json`及完整`evidence`。`collect`与`stage`的输出目录须为空，防止混入旧数据。控制文件可通过全局参数`--control <path>`指定，参数放在子命令之前。

`build`在组装之后调用独立`verify`函数，重新读取当前审批、canonical PCM、实际码流、全部PTS、代表帧和完整AAC音轨，不信任生成阶段的布尔值，通过才写成功meta。工作流不重复解码同一成品。需要对现有视频重新独立核验时可单独运行`整套精听.py verify 2009 --parts parts --original in/audio/原音.wav --out work`，不重做视频。

组装器输出`work/meta.json`：

```json
{
  "schema": 1,
  "kind": "intensive_full",
  "id": "2009",
  "year": 2009,
  "label": "2009年 专八听力 精听.mp4",
  "mp4": "tem8-intensive-full-2009.mp4",
  "mp4_sha256": "实际64位SHA256",
  "mp4_bytes": 123456,
  "source_sha256": "实际canonical WAV的64位SHA256",
  "source_record": {"说明":"由实际原音准备记录产生的完整来源对象，须与三个子段登记一致"},
  "parts": [
    {"id":"2009-A","mp4_sha256":"实际子段摘要","approval_payload_sha256":"实际当前子段审批摘要","meta_sha256":"实际子段meta字节摘要"},
    {"id":"2009-B1","mp4_sha256":"实际子段摘要","approval_payload_sha256":"实际当前子段审批摘要","meta_sha256":"实际子段meta字节摘要"},
    {"id":"2009-B2","mp4_sha256":"实际子段摘要","approval_payload_sha256":"实际当前子段审批摘要","meta_sha256":"实际子段meta字节摘要"}
  ],
  "verification": {"ok":true,"draft":false,"report":"verification.json"}
}
```

`verification.json`必须绑定实际整套MP4的`sha256`和canonical的`source_sha256`，`ok=true`、`draft=false`、`parts_order`为本年三个ID，`parts`与组装器meta中的真实来源逐项相同，`engine_sha256`为当前真实组装器字节摘要。报告还须给出实际检查与`video_lossless`、`pcm_reconstruction_verified`、`audio_verified`、`av_sync_verified`。单个全局`ok`不足以作为独立音画核验；旧报告不能重新盖成新引擎/新子段指纹。技术检查细节由组装器写入报告，不由发布器补造。

发布stage采用`kind=intensive_full`、`id=YYYY`。独立`assembly_payload_sha256`绑定三个当前子段审批、明确组装契约版本、实际组装器、原音准备及导入的数据/保护区间契约`精听数据.py`的SHA，不冒充子段的`approval_payload_sha256`。发布器文案、ZIP打包及调度工作流不属于音画生产指纹，仅修改发布环节时重新验证、复用已核整套视频。`parts`记录真实子段输入审批、视频与原音SHA；`evidence`保存组装原始meta/检查JSON、三个子段实际meta、原输入、分屏/时轴/原音报告和全部已审PNG。复用缓存时核完整证据摘要、当前审批、实际PNG集合、服务器MP4摘要与大小。

## 正式15套下载

正式目标固定为`tem8-listening-intensive-2009-2024`。发布器先一次性收齐并验证15份完整年度成品，以及45个真实子段的一对三来源映射；任何缺项、顺序错误、旧审批或未通过独立音画核验都在更新正式Release前拒绝。

MP4资产使用`tem8-intensive-full-YYYY.mp4`。ZIP使用中文成员名`专八听力精听/YYYY年 专八听力 精听.mp4`，按实际体积分包，每包不超过1.8GiB，UTF8、不压缩、固定时间戳。单个整套MP4必须留出分包安全余量；超限时失败，不擅自降画质或把一年拆成多个交付视频。`TEM8-manifest.json`和`TEM8-filenames.txt`都只列15个最终视频，内部45来源仅作证据映射。

上传沿用已核发布器的ASCII资产名与摘要复用逻辑。每个资产核服务器SHA和大小，ZIP从Release回下载后核整包SHA、CRC、全部成员视频SHA、中文名、UTF8标志、顺序、时间戳和压缩方式，最后持久保存`发布回下载核验.json`。发布失败只重试汇集/上传，不重新生成已经通过核验的子段或整套。

离线正反例：`python 专八/听力/批量/tools/整套精听发布测试.py`；此测试不接触GitHub、不发布Release、不生成教学音视频。

2009年历史原件的整套音画技术验证另存`核验/整套拼接/2009-历史缓存技术验证.json`，真实视频包对接存`2009-发布接口技术对接.json`；二者都明确`technical_only`，不是新30fps子段的生产成品或审批。可用测试脚本的`--technical-report <技术JSON> --video <实际技术MP4> --out <空闲目录>`重现真实中文ZIP往返核验；它只验证本地实际文件、不写生产stage/缓存/Release，也不把本地往返冒称服务器回下载。正式样例必须等待新的三个当前gate子段。
